# Арена Работы

Платформа разовых сезонных смен на карте: работодатели публикуют смены точкой на карте, исполнители откликаются, получают найм, общаются в чате, сдают работу и получают оценку. Оплата — напрямую между сторонами.

Техзадание и прототип — в [`design/README.md`](design/README.md) и `design/design/`.

## Стек

- **Next.js 16** (App Router, TypeScript) — фронтенд и API (`app/api/*`).
- **PostgreSQL 16** + `cube`/`earthdistance` для гео-поиска (есть в contrib любого Postgres, в т. ч. Yandex Managed PG / Selectel — для 152-ФЗ).
- Без ORM: SQL-миграции в `db/migrations`, драйвер `pg`.
- Пароли — `scrypt` (stdlib), сессии — httpOnly-cookie с хэшем токена в БД, коды подтверждения — HMAC в БД.
- SMS: провайдер `console` (разработка) или `smsru` (SMS.ru: `sms/send` и звонок-сброс `code/call`).

## Запуск

```bash
cp .env.example .env.local
docker compose up -d          # Postgres (или свой: DATABASE_URL)
npm install
npm run db:migrate
npm run db:seed               # демо: исполнители daniyar_s, olga_k; работодатель aigul_t; пароль demo123
npm run dev                   # http://localhost:3000
npm run cron                  # разовый прогон фоновых задач (для внешнего планировщика)
```

В режиме разработки код из SMS печатается в лог сервера и показывается под полем кода (`Режим разработки: код …`).
`SMS_DEV_FIXED_CODE=1234` — фиксированный код, как в прототипе.

> `dev`/`build` идут через webpack: Turbopack в Next 16.3 падает на кириллице в code frame.

## Что готово (этап 1: БД и авторизация)

- Полная схема БД по модели из ТЗ: пользователи и профили, заказы, отклики, найм/бригады, сдача/приёмка, отмены/отказы, неявки, расчёт, чат, фото, отзывы, жалобы, журнал, объекты, настройки уведомлений.
- Регистрация: роль → контакты (проверка уникальности телефона/логина в любой роли) → профиль → код по SMS/звонку + оферта. Аккаунт создаётся только после кода.
- Вход по логину или телефону (сравнение по последним 10 цифрам), роль берётся из аккаунта.
- Восстановление пароля: логин/телефон → код на привязанный номер → новый пароль; все старые сессии сбрасываются. Существование аккаунта не раскрывается.
- Ограничения: 3 попытки на код, срок 5 минут, повтор через 60 с, лимиты частоты на вход и отправку кодов (в БД — работает на нескольких инстансах), CSRF-проверка Origin.
- Модерация текста на клиенте (поле откатывается, попап) и на сервере (все текстовые поля анкеты), unit-тесты на наборы из ТЗ.

## Этап 2: заказы, поиск, карта

- Публикация заказа работодателем: клик по карте или поиск адреса → форма в 4 шага (Место → Работа → Деньги и время → Доступ) с проверкой по шагам, календарём «Сегодня/Завтра» и черновиком при закрытии («Продолжить / Удалить»). Свой тип работы попадает в справочник и в фильтр после публикации.
- Правка условий — пока никого не наняли (откликнувшимся уходит уведомление). Отмена с причиной и сроком предупреждения; поздняя отмена при нанятых — пометка на 90 дней. Принятую работу отменить нельзя.
- Поиск: радиус от базы (`earth_box` + `earth_distance`, GiST-индекс), тип работы с автодополнением (Enter — первый, Backspace — удалить последний), оплата от, «сегодня и завтра», текстовый поиск (с модерацией). Счётчик «найдено N», метки активных фильтров с ×, «Снять всё».
- Карта: MapLibre + OpenFreeMap, перенос компонента прототипа — плашки «ставка + тип», группировка на мелком масштабе, веер на одном адресе, «моя база», круг радиуса; атрибуция OSM видна.
- Карточка заказа: условия, «Все условия заказа →», работодатель (клик → профиль), кнопка отклика с единым статусом, «Отказаться» до найма, «Набор закрыт» с похожими заказами, список откликнувшихся для владельца. Телефон встречающего — только нанятому и владельцу.
- Отклик: только исполнитель, не на отменённый/закрытый/набранный/прошедший заказ, не повторно; своё условие работодателя подтверждается галочкой. Гость → регистрация/вход → отклик отправляется автоматически (если нет условия).
- Ширина < 720 px: карта сверху, панель снизу (как в макете).

## Этап 3: смена от найма до отзыва

- Найм из карточки заказа или вкладки «Отклики»: «Нанять / Отказ / Сделать старшим / Не вышел», «Отказать остальным». Не больше `crew`; нанятого нельзя отклонить — для него «Не вышел» (снимает только его, +1 к неявкам, набор открывается).
- При найме открывается чат с первым сообщением работодателя. Чат — плашка «Сообщения» внизу и значок в шапке со счётчиком непрочитанных; сообщения, отметки «прочитано», найм, сдача и приёмка приходят без перезагрузки (SSE + Postgres LISTEN/NOTIFY — работает и на нескольких инстансах).
- Телефон встречающего — только нанятому; в бригаде — только старшему, он же сдаёт работу за всех.
- Исполнитель: «Сдать работу» → у работодателя 7 дней на приёмку, иначе автоприёмка (засчитывается исполнителю). Отказ от смены после найма — с причиной и сроком; меньше суток — пометка на 90 дней.
- Работодатель: «Принять работу» (если кто-то нанят и смена не отменена), перенос даты с уведомлением нанятых и откликнувшихся.
- После приёмки: расчёт (обе стороны отмечают «оплата передана / деньги получены»), отзыв 1–5 с текстом (10 минут на правку), жалоба (одна по смене, уходит в поддержку).
- «Мои смены / Мои заказы»: этапы Отклик → Найм → Работа принята, отменённые зачёркнуты с причиной и датой; сверху то, что требует действия.
- Фоновые задачи с `pg_try_advisory_lock`: автоприёмка, очистка сессий, кодов и счётчиков лимитов.

## Этап 4: профиль, журнал, уведомления, фото

- Профиль по прототипу: фото (сжимается в браузере до 640 px, тип проверяется по сигнатуре файла), имя, роль · город, теги навыков и городов (снимаются крестиком, «+ навык»), «Вход и контакты» (логин, e-mail; телефон — только через код на новый номер и текущий пароль; смена пароля завершает другие входы), «Свой инвентарь» / «Организация» (тип, название, ИНН, доступ, инвентарь), «История смен» с отметкой о расчёте, «Пометки площадки» (90 дней), «Отзывы», «Договор» — шаблон ГПХ. Справа — сводка: смены, рейтинг, отзывы, неявки.
- Шапка: чип профиля с фото ведёт на `/profile`, «Выйти» — в профиле.
- «Журнал» и «Настройки» — правая панель из тулбара карты. Журнал: последние события, непрочитанные выделены, счётчик на кнопке растёт живьём, «Очистить», клик — открыть заказ. Свои действия пишутся в журнал сразу прочитанными и без всплывающего уведомления.
- Настройки: оповещения вкл/выкл, каналы (всплывающие в открытой вкладке, SMS, e-mail), радиус от дома 10–300 км со списком «Рядом сейчас», тихие часы (срочное — по разрешению), лимит в день, смена базы (адрес/посёлок через геокодер), обозначения карты.
- Доставка: событие → запись в журнал → очередь `notification_outbox` (SMS через SMS.ru, e-mail через SMTP). Тихие часы откладывают отправку до утра (часовой пояс `APP_TIME_ZONE`), сверх дневного лимита событие помечается «без доставки». Очередь разбирается каждые 30 с: записи арендуются `FOR UPDATE SKIP LOCKED`, отправка — вне транзакции, повтор с экспоненциальной паузой до 5 попыток. Жалобы уходят письмом в поддержку (`SUPPORT_EMAIL`).
- «Новая смена рядом»: исполнителям, у кого база в радиусе оповещений (навык по типу работы ставит выше, не отсекает).
- Фото «до/после» в смене: прикладывают и видят только работодатель и нанятые; удалить может автор, пока работа не принята. До 10 фото каждого вида, до 8 МБ (в браузере сжимаются до 1600 px). Файлы — в `UPLOAD_DIR`, отдаются с `nosniff` и `CSP default-src 'none'`.

## Этап 5: мобильная версия, рабочий режим, реклама

- Телефон (< 720 px, вошедший пользователь): узкая полоса «Арена Работы · раздел» с колокольчиком журнала и нижнее меню «Карта · Смена · Отклики · Чат · Проф.» со счётчиком непрочитанных. Чат открывается на весь экран над меню, с быстрыми ответами («Подтверждаю выход», «Буду через 20 минут» …). Шапка и нижнее меню переключаются CSS-медиазапросом — без мигания при загрузке.
- Экран «Смена» (`/shift`): самая актуальная смена — для исполнителя нанят → принята без отметки расчёта → ждёт ответа на отклик; для работодателя сдана → идёт → принята без расчёта. Чек-лист «Перед выходом» (инструктаж, СИЗ) отмечает исполнитель, работодатель видит отметки нанятых; подсказка «Первый выход»; сдача/приёмка, фото до/после, расчёт, отзыв и чат — те же блоки, что в карточке.
- Рабочий режим (в «Настройках», хранится на устройстве): крупные кнопки, поля и строки списка, крупная кнопка «Взять заказ» / «Отклики» над меню, без рекламы.
- Реклама по 38-ФЗ: креатив показывается только с erid, пометкой «Реклама» и названием рекламодателя; ссылка `rel="sponsored"` ведёт через `/api/ads/[id]/go` (клик засчитывается, к адресу добавляется erid, открытого редиректа нет). Показ засчитывается, когда блок виден наполовину, один раз за загрузку страницы, с лимитом по IP. Статистика по дням (`ad_daily`) — для отчётов в ЕРИР через ОРД. Места: список заказов (после 3-го) и профиль; аудитория — все, исполнители или работодатели.
- Управление рекламой без админки: `npm run ads -- list | add ad.json | off <id> | on <id> | report 2026-10-01 2026-10-31`. Сид для разработки добавляет демо-креативы (erid `DEMO-…`, ссылка на example.org) — в продакшене их нет.
- Ревью: рассылка событий переписана на пакетный SQL (новая смена рядом с 500 получателями — 3 запроса вместо ~2 500); живые уведомления больше 100 получателей больше не обрезаются (делятся на части); журнал хранится 180 дней; брошенные файлы (оборванная загрузка, удалённые заказы и пользователи) убираются раз в сутки; лимиты на загрузку фото и смену базы.

## Этап 6: объекты, подтверждение e-mail, самозанятость, веб-пуш

- «Мои объекты» работодателя (как в прототипе): список в левой колонке карты, «Создать заказ» — форма сразу с адресом, меткой, объёмом, доступом, инвентарём и встречающим; «Карточка» — правка объекта и смены по нему. В форме нового заказа — «Сохранить адрес как объект». Заказ хранит ссылку на объект (`jobs.object_id`), чужой объект привязать нельзя.
- E-mail: письма об уведомлениях уходят только на подтверждённый адрес — иначе можно было бы «подписать» чужой ящик. Письмо со ссылкой отправляется при регистрации, при смене адреса и по кнопке в профиле; ссылка одноразовая, живёт 24 часа и не подтверждает адрес, если его успели сменить.
- Самозанятость: ИНН (с проверкой контрольных цифр) → открытый сервис ФНС `statusnpd.nalog.ru`. Бейдж «самозанятый ✓» виден работодателю в откликах, пока проверка свежее трёх суток; подтверждённые перепроверяются раз в сутки (cron, под лимит ФНС — 2 запроса в минуту на площадку). Если ФНС не отвечает, статус не меняется.
- Веб-пуш: Service Worker (`public/sw.js`), подписка «Включить пуш на этом устройстве» в «Настройках», канал `push` в очереди доставки с теми же тихими часами и дневным лимитом; отозванные браузером подписки удаляются. Нужны ключи VAPID (`npx web-push generate-vapid-keys` → `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`); без них пуш выключен, уведомления остаются в открытой вкладке.

## Этап 7: кабинет поддержки, объектное хранилище, ревью

- Кабинет поддержки `/support` — только для сотрудников (`npm run staff -- add <логин>`; остальным страница отвечает 404). Вкладка «Поддержка» в шапке и кнопка в профиле.
  - Жалобы: очередь новых (с автором, тем, на кого жалоба, — для жалобы исполнителя это работодатель заказа, — и счётчиками жалоб и пометок), решение с обязательным комментарием. Подтверждённая жалоба ставит пометку на 90 дней; обе стороны получают уведомление с решением.
  - Пользователи: поиск по логину, имени, e-mail, телефону; блокировка с причиной — вход закрывается (сессии удаляются, открытый живой поток закрывается в течение 5 минут), открытые заказы работодателя снимаются площадкой с уведомлением откликнувшихся, ожидающие отклики исполнителя снимаются. Разблокировка возвращает вход. Все действия сотрудников пишутся в журнал (`staff_actions`) и видны в карточке пользователя.
  - Реклама: показы, клики и CTR по креативам за период, выгрузка CSV для ОРД.
- Хранилище файлов: локальная папка (`UPLOAD_DIR`) или S3-совместимое (Yandex Object Storage, VK Cloud, Selectel, MinIO) — достаточно задать `S3_BUCKET` и ключи. Уборка брошенных файлов работает в обоих вариантах.
- Ревью: письмо подтверждения больше не уходит повторно при сохранении профиля с тем же адресом; при выходе снимается пуш-подписка браузера (уведомления не придут следующему человеку на устройстве); смена адреса объекта переставляет его точку; экран «Смена» не перезагружается от событий по чужим заказам.

## Этап 8: споры по расчёту, мониторинг, производительность

- Споры по расчёту (как в прототипе): после сдачи работы исполнитель («Оплата не пришла — открыть спор») или работодатель («Открыть спор по расчёту», с выбором нанятого) указывает причину, сумму и описание. В спор уходит снимок доказательств: фото до/после, переписка, приёмка, отметки о расчёте, условия заказа. Вторая сторона получает срочное уведомление и может ответить: работодатель — «Оплата отправлена» (спор закрывается, расчёт отмечается), любая — пояснение (спор уходит на разбор). Инициатор может снять спор («Деньги пришли» ставит отметку получения). Не больше одного незакрытого спора на пару в заказе; незакрытый спор виден в профиле обеих сторон. В кабинете поддержки — вкладка «Споры»: решение в пользу одной из сторон, проигравшей — пометка на 90 дней, обеим — уведомление.
- Мониторинг: `/api/health` (200/503 по доступности БД — для балансировщика), `/api/metrics` в формате Prometheus по `Authorization: Bearer $METRICS_TOKEN` (без токена — 404): запросы API по классу ответа, гистограмма длительности, пул БД, живые потоки, очередь уведомлений, очередь поддержки, память. Пул БД и предел длительности запроса настраиваются (`DB_POOL_MAX`, `DB_STATEMENT_TIMEOUT_MS`).
- Нагрузочная проверка: `npm run load -- --seed 50000` (синтетические заказы, не в продакшене) и `npm run load -- --url … --seconds 20 --concurrency 32`.
- Оптимизация поиска по результатам нагрузки (50 000 заказов, один процесс Node): точка заказа хранится готовой (`jobs.pt`), радиус применяется к 500 ближайшим, а не ко всему кругу, — поиск с радиусом 150 → 20 мс; ответы API больше 2 КБ сжимаются gzip в пуле потоков (выдача карты 272 → 24 КБ, на мобильной сети — в разы быстрее; за nginx с gzip можно выключить `COMPRESS_JSON=0`). Узкое место — процессор одного процесса Node; масштабируется запуском нескольких экземпляров (живые события, фоновые задачи, лимиты и файлы уже рассчитаны на это).
- Надёжность клиента: действие считается успешным только по JSON-ответу сервера — HTML-страница прокси или перезапуска больше не выглядит как «сохранено».

Изменения заказов сбрасывают кэш. Нагрузочная проверка (50 000 заказов, один процесс): ~640 запросов/с вместо ~125, поиск p50 42 мс вместо 263.

Нанятый может снять день («Не смогу» / «Вернуть»), работодатель видит, сколько не выйдут в какой день, и получает срочное уведомление; три снятых дня подряд — пометка в профиле. «Продлить серию на месяц» добавляет 4 выхода и зовёт тех же исполнителей.

## Этап 10: повторное ревью, замена на день серии, работа поддержки

- Ревью:
  - `current_date` в SQL считался по часовому поясу сервера БД (UTC), а сроки в коде — по Москве: с полуночи до 3:00 они расходились на сутки (экран «Смена», серии, статистика). Теперь каждое соединение пула работает в `APP_TIME_ZONE`.
  - Гонка на уникальных значениях (два человека одновременно берут один логин) и таймаут запроса давали «Что-то пошло не так» (500) — теперь понятные 409 и 503 с `Retry-After`.
  - Линтер проверял скопированные файлы воркера карты — исключены; устаревшая директива в карте убрана.
- Замена на день серии: после «Не смогу» день получает свободное место — его видят все (даже гости: «свободно мест: 1»). Исполнитель не из смены жмёт «Выйти в этот день», работодатель видит откликнувшихся под днём и «Берёт на день» — взятому открывается чат с работодателем; остальным — отказ. Вернуть снятый день нельзя, если на него уже взяли замену.
- Кабинет поддержки: срок ответа («3 рабочих дня», выходные не считаются) на каждой жалобе и споре с отметкой просрочки; «Взять себе», «Снять», передать другому сотруднику, фильтр «Мои»; шаблоны ответов (для жалоб, споров или для всех) — вставляются в решение одним нажатием, вкладка «Шаблоны».

## Этап 11: ревью серий, напоминания поддержке, приёмка по дням

- Ревью:
  - Кэш выдачи для гостей сбрасывался внутри транзакции — параллельный запрос успевал закэшировать ещё не зафиксированное состояние на 20 с. Теперь сброс — после `COMMIT` (`afterCommit` в `server/db.ts`), при откате не выполняется.
  - Исполнитель уходил из серии (отказ, «Не вышел») — его снятые дни оставались «свободными местами», и на них можно было взять лишнюю замену. Теперь снятые дни ушедшего закрываются (кроме дней, где замена уже взята, — она остаётся за своим днём). Взятый в основной состав больше не числится заменой на отдельные дни.
  - Замена на день не видела себя: в «Моих сменах» и на экране «Смена» её заказа не было. Теперь есть — с днями и решением работодателя («Вы на замене», блок «Замена» с чатом).
  - Отмена заказа и снятие площадкой не доходили до замен — теперь доходят. Блокировка исполнителя снимает его с идущих смен и будущих замен (без пометок), работодатели получают срочное уведомление и открытый набор.
  - Карточка заказа: отклики, блок смены и серия грузятся одновременно, а не по очереди.
- Напоминания поддержке о сроке ответа (фоновая задача): за сутки до срока и когда срок прошёл — по разу на обращение. Назначенное — только своему сотруднику (при передаче другому — ему заново), остальные — всем сотрудникам; одно сводное уведомление на человека, ссылка ведёт в кабинет поддержки. В кабинете такие сроки выделены.
- Приёмка и расчёт по дням серии: каждый выход сдаётся отдельно («Сдать день» — с дня выхода, тот, кто в этот день выходит; в бригаде — старший, а если он этот день снял — любой из выходящих, в том числе замена). Работодатель «Принимает день» (или день засчитывается сам через 7 дней после сдачи), затем обе стороны отмечают расчёт за день. Сводка «ждут приёмки / отметить расчёт» — в блоке серии; блок есть и на мобильном экране «Смена». «Завершить серию» закрывает заказ: сданные дни принимаются, открываются отзывы; расчёт по заказу — сводка по дням, отметка по заказу ставится сразу за все принятые дни. Спор по расчёту — после первого сданного дня. Сданный день уже нельзя снять или отдать на замену.

## Этап 12: ревью, строгая CSP, вызовы «по снегопаду», отзывы замен

- Ревью:
  - Перенос начала серии или смена её графика сдвигали все даты, а снятые дни, замены и сданные выходы привязаны к конкретным датам — они «отрывались» (сданный день нельзя было ни увидеть, ни принять). Теперь, если по серии уже есть такая история, даты не сдвигаются — понятный отказ.
  - Спор по серии: снимок доказательств смотрел только на приёмку заказа целиком («работа не принята», даже если дни приняты и оплачены). Теперь — сдано, принято и оплачено по дням этого исполнителя.
  - Шаблон договора не открывался замене на день; для серии срок — «по графику», для замены — её дни.
  - «Мои заказы» и «Отклики» у крупного работодателя сортировали все его заказы целиком со всеми соединениями. Теперь сначала узкая выборка 300 нужных, потом детали: на 50 000 заказов 177 → 30 мс.
- Строгая CSP для скриптов: `proxy.ts` выдаёт каждой странице свежий nonce, `script-src 'nonce-…' 'strict-dynamic'` — чужой встроенный скрипт не выполнится, даже если попадёт в разметку. Стили прототипа заданы атрибутами `style`, поэтому `style-src` оставлен с `'unsafe-inline'`. Внешние источники — шрифты Google и стиль/тайлы карты (`NEXT_PUBLIC_MAP_STYLE_URL`; дополнительные хосты — `CSP_CONNECT_SRC`). Нарушения браузеры присылают в `/api/csp-report` — счётчик `arena_csp_violations_total` в метриках. Все страницы рендерятся по запросу.
- Выходы «по снегопаду»: работодатель вызывает бригаду на дату (не дальше месяца вперёд) — нанятым приходит срочное уведомление. Вызов становится днём серии: его снимают («Не смогу»), берут на замену, сдают, принимают и рассчитывают так же, как день по графику. Вызов можно отменить, пока день не наступил и не сдан, — снятия и замены на него уходят вместе с ним, все участники получают уведомление. Серии «по снегопаду» не продлевают: вызовов до 60.
- Отзывы для замен: замена оценивает работодателя (а он — её) сразу после приёмки дня, в который она выходила, не дожидаясь конца серии; основной состав — как раньше, после завершения. Отзыв — в блоке серии (карточка и экран «Смена»). Жалоба на замену или от неё — по тем же правилам.

## Этап 13: ревью серий, счётчик смен с заменами, жалобы замен, CSP для стилей

- Ревью:
  - Серия, у которой все даты прошли, навсегда оставалась в поиске как открытая и принимала отклики. Теперь у заказа есть дата последнего выхода (`series_end`, пересчитывается при публикации, правке, переносе и продлении): закончившаяся серия уходит из поиска и счётчиков фильтра, отклик на неё — понятный отказ. Серия с нанятыми закрывается сама через 7 дней после последнего выхода — открываются отзывы (сданные дни принимаются, как при «Завершить серию»).
  - Вызовы «по снегопаду» ограничены по частоте (20 вызовов и отмен в сутки на заказ): каждый — срочное уведомление бригаде.
- Счётчик закрытых смен исполнителя (карточка отклика, профиль, кабинет поддержки) считает разовые принятые смены и принятые дни серий, в которые он выходил, — в том числе на замену. Один общий SQL-фрагмент вместо четырёх копий, GIN-индекс по вышедшим в день.
- Жалоба для замены в блоке серии: замена — на работодателя, работодатель — на замену, после приёмки её дня; отметка «жалоба на рассмотрении». Форма жалобы — общий компонент для блока смены и серии.
- CSP для стилей: теги `<style>` и таблицы стилей — только со своего сайта, Google Fonts или с nonce ответа (`style-src-elem`): внедрённый `<style>` с селекторами-«шпионами» не применится. Атрибуты `style`, которыми интерфейс прототипа задаёт оформление, разрешены (`style-src-attr`); браузерам без этих директив остаётся общий `style-src`. Оформление контролов карты перенесено из тега, вставляемого на лету, в `components/map/map-skin.css`; свои страницы 404 и ошибок (встроенные страницы Next.js вставляют `<style>` без nonce).

## Этап 14: безопасность входа и пуша, нагрузка на пул, стили в CSS-модулях

- Ревью:
  - Веб-пуш (SSRF): адрес подписки проверялся только по тексту имени хоста — десятичный IP (`https://2130706433/…`), `0.0.0.0`, IPv6-форма или домен, указывающий во внутреннюю сеть, проходили, и сервер слал запросы внутрь. Теперь отправка идёт через агент `server/safe-agent.ts`: адрес проверяется после DNS-разрешения (частные сети, localhost, link-local, CGNAT, IPv4 внутри IPv6), такая подписка удаляется. Агент держит соединения с пуш-сервисами открытыми.
  - Лимит попыток входа на аккаунт проверялся до проверки пароля, а списывался после — пачка параллельных запросов проходила проверку разом и перебирала больше 10 паролей. Теперь попытка списывается атомарно до проверки, успешный вход её возвращает.
- Стили прототипа: 843 статичных `style={css('…')}` перенесены в CSS-модули рядом с компонентами (`scripts/css-modules.mjs`). Правило — `:where(.класс) { … !important }`: нулевая специфичность и `!important` в точности повторяют приоритет атрибута `style` (сильнее обычных правил, слабее чужих `!important` вроде `.only-narrow`). Глобальные правила, искавшие элементы по тексту `style`, получили классы-метки (`.fh`, `.ph-accent`, `.scroll-pane`). Проверка — попиксельная сверка 33 экранов (гость, работодатель, исполнитель, мобильная версия, кабинет поддержки) до и после: совпадают, кроме меток времени. HTML гостевых страниц легче на 4–12 %. Динамические стили (~250, со склейкой строк) остаются атрибутами.
- Оптимизация: карточка заказа для участника смены — восемь однострочных запросов объединены в один: меньше соединений пула на открытие карточки, под нагрузкой (32 параллельных) ~345 → ~430 открытий/с.
